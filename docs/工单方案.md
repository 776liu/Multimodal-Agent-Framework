## 二、工单详情

### T-01 Agent 维度可观测性打通 `P0` 1d

**目标**：把后端已经记录、但完全没有出口的多 Agent 事实暴露出来——
让「哪个 Agent 派发了什么、调了哪个模型、花了多久、成败如何」成为可查询数据。

**背景（两处缺口）**：

1. **调用链缺 agent 字段**：`CallChainEntry` 目前只有 `model_name / capability / status /
   error_code / attempted_at`。这正是**单 Agent 多模型调度器**也会有的数据，因此当前
   前端观测面板无法证明"多 Agent"的存在。必须补 `agent`（角色名）与 `elapsed_ms`。
2. **进度事件全被丢弃**：`Orchestrator._emit()` 已发出 `planning / planned / dispatching /
   collecting / auditing / revision` 等事件并携带 `agent` / `step` / `total` 字段，
   但 `Worker` 调用 `agent.run()` 时**未传 `on_progress`**，事件在进程内蒸发。

**范围**：
- `src/core/models.py`：`CallChainEntry` 新增 `agent: str = ""`、`elapsed_ms: int = 0`；
- `src/core/base_agent.py` / `agents/*`：`_record_chain()` 写入调用链时带上自身角色名与耗时；
- `src/core/builder.py`：日志序列化补齐新字段（注意老数据反序列化的默认值兼容）；
- `src/api/worker.py`：构造进度回调，将事件写入 Redis 进度通道
  （如 `agent:progress:{task_id}`，List 结构，TTL 与任务一致）；
- `src/api/main.py`：新增 `GET /api/task/{task_id}/progress` 端点返回事件数组；
- `src/api/main.py`：新增 `GET /api/task/{task_id}/agents` 端点，读取
  `Storage.get_agent_messages(task_id)`，输出按阶段分组的调度轨迹
  （含 `from_agent / to_agent / message_type / 耗时 / 产物类型`）；
- 事件结构统一为 `{stage, agent, step, total, status, ts}`。

**验收标准**：
- [x] `call_chain` 每条记录带 `agent` 字段，历史回放可见角色名
      —— 实测：`agent=writer_agent  deepseek-ai/DeepSeek-V3  1284ms`；
- [x] `GET /api/task/{id}/agents` 返回真实 `agent_messages` 记录
      —— 实测 6 条，含 orchestrator / writer_agent / reviewer_agent 调度轨迹；
- [x] 三步任务事件序列可见 `image_agent` / `writer_agent` / `video_agent`
      依次 dispatch 与 collect —— 实测 9 条事件全部带 agent 字段；
- [x] 进度记录随任务 TTL 自动过期清理（Redis List + TTL 与任务一致）。

**实施补充（超出原范围的三处，均由实测发现）**：
1. **落库侧序列化同步补齐**：原范围只列 `builder.py`，实际调用链有两处独立序列化
   （`builder.py` 响应侧 + `storage.py` 落库侧），只改前者会导致历史回放看不到角色名。
2. **历史回放归一化**：`get_task_history` 原直接透传 `log_json` 原始 dict，
   老数据缺 `agent` 键会让前端取值 KeyError；已补默认值兜底，
   并支持从专用列 `call_chain_json` 回退读取（该列此前从未被读取）。
3. **任务ID映射**：Redis 队列ID 与引擎内部 `task_id` 是两套 ID，
   而 `agent_messages` 记录的是内部ID。新增 `link/resolve_internal_task_id`，
   否则前端用外部ID 永远查不到多 Agent 轨迹（实测返回空）。

**依赖**：无
**风险**：低。纯增量改动，不影响任务执行主链路；主要风险是老任务的 `call_chain`
反序列化缺字段，靠默认值兜底即可。

### T-02 前端多 Agent 可视化 `P0` 2d

**目标**：让多 Agent 架构在界面上**被看见**，且不做任何虚构——
所有渲染内容均来自 T-01 暴露的真实数据。

**设计原则（重要）**：
- **中性命名**：侧栏标题由「多智能体调用链」改为「**调用链路**」。
  界面不喊口号，内容自己证明系统是多 Agent；
- **如实呈现**：只可视化后端已记录的事实（agent_messages / call_chain / revision 事件），
  不做演示性装饰。答辩时被追问"这是设计还是表演"，可视化的是真实日志，可当场验证；
- **证据配锚点**：每个可视化元素必须附带"设计带来的好处"对照
  （如「⚡ 0.3s 自动降级，用户无感知」「质量分 3.2 → 4.8」），
  否则只证明了"多调了一次模型"，无法证明"多 Agent 有价值"。

**范围**：

1. **`AgentInspector.tsx` — 调用链路面板（改造既有区块，不新增并列面板）**
   - 标题改为「调用链路」，取消上下双区块结构；
   - 按 **Agent 角色分组**（而非按模型平铺），每组展示：
     角色名 → 调用的模型 → capability → 状态 → 耗时；
   - 降级环节标注对比锚点（如「自动切换备用模型 · 0.3s · 用户无感知」）；
   - 数据来自 T-01 的 `call_chain[].agent`，非运行时轮询。

2. **`ChatArea.tsx` + `ChatBubble.tsx` — 对话流角色卡（新增）**
   - 每个子任务产出后，在气泡上方插入**可折叠**的角色卡；
   - 默认折叠为一行摘要，避免四个角色全展开淹没对话流：
     `▸ 🎯 Orchestrator · 4 个 Agent · 14.2s · ✓ 全部成功 [展开]`
   - 展开后显示该角色的职责、输入 prompt 摘要、耗时、产出 Artifact 缩略图；
   - 数据来自 `/agents` 端点的调度轨迹。

3. **反思重试可视化（同卡内时间线）**
   - 重试必须画成**同一张卡内的竖向时间线**，而非两张重复卡片：
     ```
     ✍️ writer_agent
        ├─ 第 1 次  ✅  产出分镜脚本 (3.2s)
        └─ 审查后被要求修订 → 第 2 次  ✅  产出终稿 (2.8s)
     ```
   - 关键是让重试呈现为**因果链**（发现问题 → 修正），而非「重复劳动」；
   - 配合质量分对照（如 3.2 → 4.8）强化"反思闭环有效"的论证。

4. **状态管理**：`taskStore.ts` 累积 `/progress` 事件至 `progressEvents`，
   轮询结束后用 `/agents` 轨迹补全最终态。

**验收标准**：
- [x] 侧栏调用链路按角色分组，各角色的模型、耗时、状态齐全
      —— 实测 3 角色 4 次调用：`writer_agent 46.3s / image_agent 11.5s / reviewer_agent 13.5s`；
- [x] 对话流出现可折叠角色卡，默认一行摘要（`🎯 Orchestrator · 4 个 Agent 协作 · xx.xs`），
      展开后与侧栏链路数据同源（均来自 T-01 的 call_chain[].agent 与 /agents 轨迹）；
- [x] 审查打回场景在同一张卡内以竖向时间线呈现「发现问题 → 修正」因果链；
- [x] 刷新页面后可从后端恢复（切换会话/挂载时按最新 task_id 拉取 /progress + /agents）；
- [ ] **保底验证**：若角色卡来不及做，仅"调用链路面板 + agent 字段"也应足以
      在答辩中证明多 Agent 存在（此为 T-02 的最低可交付形态）。

**依赖**：T-01
**风险**：低—中。前端纯增量；主要风险是对话流信息过载，靠默认折叠控制。

### T-03 视频产物本地化归档 `P0` 1d

### T-04 Reviewer 严格度校准 `P1` 1d ✅ 已完成

**目标**：解决 Reviewer 误判导致反思闭环无法收敛的问题。

**工单原记录现象**：实测中事实正确的文本（如「长城始建于春秋战国」）被打回，
理由为「长城不是世界最早建筑」——若反复打回会耗尽重试预算、浪费 Token。

**实测结论（重要，与原假设有出入，如实记录）**：
构造 80 条评测集（30 条严谨正确 + 20 条边界正确 + 30 条含实质错误）后测得的**基线误报率为 0%**，
原记录中的稳定误判**在当前代码状态下无法复现**：

| 检验 | 结果 |
| :--- | :--- |
| 30 条严谨正确文本 | 全部通过（评分 4~5） |
| 20 条边界正确文本（通俗/笼统/带限定词，易被挑刺） | 全部通过（评分 5） |
| 30 条含实质错误文本 | 全部打回（评分 1，判词准确指出木星最大、珠峰8848 等） |
| 原案例「长城始建于春秋战国」单条重复 5 次 | 5 次全部通过，其中 1 次评分从 5 波动到 3 |

**真正定位到的缺陷（本次修复目标）**：

1. **阈值形同虚设**：原代码 `passed = bool(data.get("pass", score >= 3))` ——
   模型几乎总会返回 `pass` 字段，因此**项目自己定义的评分阈值从未生效**，
   判定完全由模型自报的布尔值决定。严格度既不可配置也不可预测。
2. **评分非确定性波动**：同一文本重复审查会出现 3~5 分跳动。
   当分数落在阈值边界附近时，是否打回变成随机事件——这才是原记录误判的真实成因。
3. **Prompt 缺少"不要吹毛求疵"的明确界定**，且原 Prompt 本身要求模型输出 `pass`，
   把最终裁定权交给了审查模型。

**已实施方案**：
- **Prompt 重写**：明确"只针对实质性缺陷打回"，并列出**不得打回的四类情况**
  （表述通俗/不够全面/合理限定词/常识容许范围内的数据出入）；
  增加"不得凭空追加要求，只能基于文本自身内容判断"（针对原案例那种臆想式批评）；
  移除 `pass` 输出字段，只要求给分；
- **判定逻辑改为纯阈值驱动**：不再采信模型自报 `pass`；
  `score >= pass_threshold(4)` 直接通过；`warn_threshold(3) <= score < 4` 通过但记警告
  （放行交付、不触发反思重试，省 Token）；`< 3` 打回；
- **阈值配置化**：新增 `config/app.yaml` 的 `reviewer` 段
  （`pass_threshold` / `warn_threshold` / `enable_llm_review` / `min_text_length`），
  由 `load_reviewer_config()` 读取并注入 `ReviewerAgent`，只改 yaml 即可调松紧；
- **解析健壮性**：`_parse_verdict` 改为返回 `(score, issues)`；
  缺少 `score` 字段或评分越界视为解析异常 → 保守放行，避免审查器故障误伤产物。

**评测工具**：`scripts/eval_reviewer.py` + `tests/fixtures/reviewer_eval_set.json`
（80 条，分 good / borderline_good / bad 三档），输出 FPR / FNR / 准确率，
可直接产出论文 E5 的 CSV；支持 `--json` 导出。

**验收标准**：
- [x] 评测集上误报率 < 10%：**实测 FPR 0%（0/50）**，漏报率 0%（0/30），准确率 100%；

### T-05 快慢双车道队列 + 双 Worker `P1` 2d ✅ 已完成

**目标**：解决视频长任务阻塞文本任务的问题（毕设差异点 1）。

**现象**：原先单 Worker 串行消费。视频任务执行 5 分钟期间，
后续文本任务只能排队，导致 P95 延迟飙升。

**已实施方案**：
- `RedisTaskManager` 双队列：`agent:queue`（快车道 text/image）与
  `agent:queue:slow`（慢车道 video），队列名常量 `QUEUE_KEYS` 统一管理；
- **双层车道判定**（提交时预判 + 消费时纠偏）：
  - 提交侧：`guess_lane(user_input)` 按视频类关键词预判，任务 Hash 记录 `lane` 字段；
  - 消费侧：快车道 Worker 若按规则判定该任务应属慢车道，调用
    `requeue_to_lane()` 改派并跳过，避免自己跑 5 分钟（慢车道 Worker 关闭纠偏，防死循环）；
- `Worker` 增加 `lane` 参数绑定车道，`main.py` 启动两个线程
  （`api-worker-fast` / `api-worker-slow`），共享同一 `stop_event` 优雅退出；
- `TaskManager` 抽象层补齐 `requeue_to_lane()`，`MemoryTaskManager` 同步实现分车道语义，
  保证测试与 Redis 版接口一致。

**顺带修复的隐患**：`dequeue(timeout=0)` 原先会因 Redis `BRPOP timeout=0`
**永久阻塞**，现约定 `timeout<=0` 为非阻塞 `RPOP`，与直觉一致。

**验收标准**：
- [x] 视频任务执行中，文本任务可在独立 Worker 上并发执行；
      *实测：视频任务（slow）运行期间，文本翻译任务（fast）独立走完
      planning→writer→auditing 并返回 SUCCESS，未被阻塞*；
- [x] 两车道任务不串道、改派后状态正确重置（8 项单测覆盖，含真实 Redis 往返）；
- [ ] 文本任务 P95 延迟相比单 Worker 显著下降（**待 E2 实验量化**）。

**依赖**：T-01
**风险**：中。并发写 SQLite 需注意锁（建议开启 `busy_timeout`）。
**遗留**：`guess_lane` 是关键词规则，非语义判定；若 PLANNING 后发现实际为视频任务，
当前只能靠提交侧预判覆盖，后续可考虑让 Orchestrator 在 planning 完成后主动改派。

**目标**：让 `pytest tests/` 全绿，恢复 CI 可用性；同时收敛 T-01/T-02 评审遗留的两项技术债。

- `test_api.py::test_submit_and_poll_text_task` — 依赖外部服务常驻。

**范围一：陈旧测试修复（原 T-08 范围）**

- 测试改为使用临时配置文件，不依赖本地 `config/model.yaml`；
- API 测试加 `skipif`（服务未启动时跳过）或改用 fixture 起服务。

**范围二：技术债 A —— model_invoked 打点收敛为基类模板方法**
（T-01/T-02 评审发现的可维护性缺陷）

现状问题：`_mark_call_start()` 分散在 4 个专业 Agent 里各自手工调用
（`model_invoked = True` + `_mark_call_start()` 两行）。
新增 Agent 时忘记这两行，`elapsed_ms` 会**静默变为 0**——
不报错、不失败，只是数据悄悄缺失。
这与「capability→output_type 映射漏掉 image」是同一类错误模式：
靠约定保证的事，缺一项就静默错。

收敛方案：BaseAgent 提供模板方法，把「打点 → 调用 → 记录」封装为一处：
```python
# BaseAgent 新增（示意）
def invoke_model(self, model_info, message) -> LLMResponse:
    self.model_invoked = True
    self._mark_call_start()
    return self.llm_client.call(
        model_name=model_info["model_name"],
        endpoint=model_info["endpoint"],
        api_key=model_info["api_key"],
        prompt=message.prompt,
        output_type=self.output_type_for(message),
        image_url=...,   # 由子类覆写钩子提供
    )
```
四个专业 Agent 改为调用 `self.invoke_model(...)`，
删除各自的 `model_invoked = True` / `_mark_call_start()` 样板。

**范围三：技术债 B —— agent_messages 增加 role 冗余字段**
（T-01/T-02 评审发现的前后端语义耦合）

现状问题：一条消息的"执行方角色"由 message_type 反推——
`result` 消息的执行方是 `from_agent`，`dispatch` 消息的执行方是 `to_agent`。
同一语义在**后端落库时不写明、前端 AgentRoleCard 再推导一次**，
两端各维护一份逻辑，任何一端调整即静默不一致。

收敛方案：`MessageBus._record()` 落库时直接写入 `role` 字段
（= 执行方 Agent 名），`agent_messages` 表加一列；
前端 `AgentRoleCard` 改读 `role`，删除反推逻辑。

**验收标准**：
- [ ] `pytest tests/` 全绿；
- [ ] 测试不产生真实 API 调用费用（或明确标记为集成测试）；
- [ ] 新写一个 Agent 时**无需手写任何打点代码**，调用链自动带 agent/elapsed_ms
      （以一个测试用 Agent 验证）；
- [ ] 前端 `AgentRoleCard` 中不再出现 `message_type === 'result' ? from_agent : to_agent`
      反推逻辑，改为直接读 `role` 字段；

**风险**：低—中。范围二触碰 4 个 Agent 的调用路径，靠既有

### T-11 多轮规划上下文约束 `P0` 0.5d ✅ 已完成

**目标**：修复多轮会话中 TaskRouter 把历史已完成任务重复排入执行计划的问题。

**现象**（T-05 验证时发现）：
同一会话先后提交「翻译 Hello World」与「生成5秒视频」，第二个任务的执行计划变成两步：
```
step1: writer_agent → "把Hello World翻译成中文"   ← 上一个任务被重做一遍
step2: video_agent  → "城市夜晚的霓虹街道，5秒"
```
白白多花一次模型调用与若干秒延迟。

**根因（四层叠加）**：
1. `build_context()` 把整个会话历史渲染成一段对话记录，直接拼在
   SYSTEM_PROMPT 结尾"现在，请分析以下用户输入："之后——「一条指令」变成「一段对话」；
2. SYSTEM_PROMPT 里 **8 个 few-shot 全是单轮示例**，从未告诉模型"历史任务已完成、不要重做"；
3. 历史开场白只写"请根据上下文理解用户当前需求"，未界定历史的作用边界；
4. few-shot 中存在 `"把这个画面做成动态短片，并配一段旁白" → 两步` 的样板，
   模型容易把历史里的两件事套进 `multi_step_multimodal` 模式合并成一个计划。

**顺带修复的隐藏缺陷**：`build_context` 的 docstring 声称"将历史对话和当前输入拼成完整上下文"，
但实现从未拼入 `current_input`，仅靠"调用方先 add 再 build"的顺序兜底。已修正实现与注释一致。

**已实施方案**：
- `task_router.py` SYSTEM_PROMPT 新增「多轮对话铁律（最高优先级）」四条：
  只拆 `<current_request>`／历史已完成任务禁止重复执行／仅"重做"时方可重排／无历史时当前即全部；
- 新增 2 个**多轮 few-shot 示例**（历史已完成翻译只拆视频／借历史理解指代但不重做），
  显式标注"不得重复排入计划"；
- `memory.build_context()` 改为结构化输出：
  ```
  <history>
  用户: ...
  助手: 上一步生成了一张图片，URL是：...
  </history>
  <current_request>当前指令</current_request>
  ```
- 历史中**剔除末尾的当前输入**（调用方已提前 add），确保同一指令只出现一次；
- 产物回填补齐 `video` 类型（此前只处理 text/image，视频 URL 不会进入历史）。

**验收标准**：
- [x] 修复后同一上下文拆解为 `single_multimodal / 1 步（video only）`（修复前为 2 步）；
      *实测意图：`multi_step_multimodal(2步)` → `single_multimodal(1步)`*；
- [x] 合理引用历史仍生效：历史有图 + "给这个画面配文案" → 单步 `text-generation`，`reference_step=0`；
- [x] 单轮场景无回归：翻译→`single_text`，图+描述→`multi_step_multimodal(2步)`；
- [x] 端到端验证：同会话任务1(翻译)完成后发任务2(生图)，计划仅 `image_agent` 一步；
- [x] 7 项单测覆盖结构化标记／指令去重／产物回填／单轮退化／Prompt 铁律存在性。

**依赖**：无
**风险**：低。仅影响规划阶段的上下文装配，不改变执行链。
**遗留**：若模型偶发仍重复历史任务，可进一步收窄为"只注入上一轮产物摘要，不注入历史指令流"。

## 二之二、协作可视化专题（T-12 ~ T-14 的设计依据）

### 背景：与主流 Agent 协作平台的可视化形态差异

参考 [Multica](https://github.com/multica-ai/multica)（开源托管 Agent 平台）与
OpenAI AgentKit 的可视化设计，三者形态差异源于**协作范式不同**：

| | 本项目 | Multica | OpenAI AgentKit |
| :--- | :--- | :--- | :--- |
| 数据模型 | **消息流**（dispatch / result） | **任务卡**（issue） | **图节点**（画布） |
| 主视图 | 阶段条 + 调用链列表 | 看板 + activity timeline | 可拖拽工作流画布 |
| 实时性 | 轮询 2s（SSE 见 T-06） | WebSocket 流式 | — |
| Agent 形象 | 角色名 + 耗时数字 | profile + 会说话的评论 | 节点 |
| 人类介入 | 事后回看 | Agent 主动 raise blocker | — |
| 范式 | **中央编排式**（Orchestrator 拆 DAG） | **任务池认领式**（Agent 自主 claim） | 可视化编排 |

**范式差异决定了可视化必然不同**：
- 编排式：可预测、可审计、硬依赖有保障 → 适合有固定 SOP 的视频生产流水线；
- 认领式：灵活、可扩展、容错好 → 但无法保证"必须先出图才能图生视频"这类硬顺序依赖。

因此本项目**不应照搬 Multica 的看板形态**，而应在"编排式"范式下补足
当前缺失的三类协作信息：**依赖关系、Agent 发言、中间状态**。

### 当前右栏已有什么、缺什么

`AgentInspector.tsx` 现有四个区块：编排管道阶段 / 调用链路 / 质检与合规审计 / 架构运行节点。
数据基本齐备，但缺"协同感"：

| 缺失 | 现状 | 对应工单 |
| :--- | :--- | :--- |
| **产物依赖的"边"** | 各步骤产物并列显示，看不出"step2 用了 step1 的图" | **T-12** |
| **Agent 的"声音"** | 只有 `角色名 · 耗时 · 状态`（日志形态），不是协作形态 | **T-13** |
| **中间状态与流动感** | 仅 成功/失败/运行中，缺"排队中/等待上游/等待确认" | **T-14** |
| 实时推送 | 轮询 2s | T-06（SSE） |

### 重要更正（数据链路核实结论）

先前判断"产物依赖连线后端零改动"**不准确**，实测核实如下：

- `reference_step` 字段**只存在于 `Subtask`（执行计划）**，存在于
  [`src/core/models.py`](../src/core/models.py) 的 `Subtask` 定义中；
- `AgentMessage` 与 `Artifact` **均未携带该字段**，`metadata` 里只有 `step/model/prompt`；
- 因此依赖关系在**执行期即丢失**，仅被 Orchestrator 内部用于挑选上游图片
  （`context.upstream_of`），前端拿不到。

**结论**：T-12 需要**后端小改**（把依赖关系透出），不是纯前端工作。

### T-14 中间状态与流动感 `P2` 1d ✅ 已完成

**目标**：补上"排队中 / 等待上游 / 等待确认"三种中间状态，并让节点逐个点亮——
"等待"才是多 Agent 协作最直观的证据（`video_agent` 在等 `image_agent` 的产物时，那个等待就是协同）。

**范围**：
- **后端（约 0.3d）**：`Orchestrator._emit()` 补充事件
  - `queued`（任务入队，含 lane 字段，T-05 已有 data）
  - `waiting_upstream`（步骤需要上游产物但尚未就绪）
- **前端（约 0.7d）**：
  - 状态枚举扩展：`排队中 / 等待上游 / 运行中 / 成功 / 失败`；
  - 阶段条按事件逐个点亮（当前步骤脉冲高亮，已完成打勾）；
  - 视频等长任务显示"已等待 X:XX"（后端 progress 已有 stage 信息）。

**实施结论（与设想不同，如实记录）**：
- **`waiting_upstream` 取消**：Orchestrator 是严格串行执行，步骤 N 只在上游完成后才派发，
  该状态在真实运行中**永远不会出现**。为一个不存在的状态写代码属于"为演示而表演"，
  与本文"只可视化真实事实"的原则冲突，故删除；
- **`queued` 无需后端改动**：任务在 Redis 队列中等待时，`GET /api/task/{id}` 的
  `status` 即为 `pending`，前端据此显示"排队中"即可，无需新增事件；
- **点亮改为按真实事件推进**：原先管道四阶段按任务状态**静态推断**
  （processing 即恒定点亮前两段），实际未反映进度；现改为按 `/progress` 的
  `planning → planned → dispatching → collecting → auditing` 事件逐步点亮，
  无事件流时（历史回放）回退到静态推断。

**验收标准**：
- [x] 任务提交后显示"排队中"（`status === 'pending'`），进入执行后切"执行中"；
- [x] 管道阶段按真实事件顺序点亮，顶部显示真实进度（如"运行阶段 3/4"）而非固定值；
- [x] 不引入额外轮询请求（复用现有 `progressEvents`）；
- [d] ~~依赖上游的步骤显示"等待上游"~~ —— 串行执行下不会发生，已取消（见上）。

**依赖**：T-01
**风险**：低。注意事件量增长后 `/progress` 体积，必要时做前端节流。

### T-15 调用链实时化 `P1` 1d ✅ 已完成

**现象**：右侧「调用链路」不是逐条跳出来的，要等任务跑完才一次性出现；
而「编排管道阶段」却是实时的——两者表现不一致。

**诊断（关键结论）**：**不是流式（SSE）的问题**。SSE 只改变"数据如何送达浏览器"，
改变不了"数据此刻是否存在"。排查三层数据后确认：

| 区块 | 实时性 | 原因 |
| :--- | :--- | :--- |
| 编排管道阶段 | ✅ 已实时 | 依赖 `progressEvents`，Worker 逐事件写入 Redis |
| 调用链路 | ❌ 完全不实时 | `call_chain` 仅在 `run()` 收尾时 `drain_call_chains()` 汇总；Worker 也只在 run 返回后才把 `result` 写入 Redis，执行期 `/api/task/{id}` 的 `result` 为空 |
| 协作对话/拓扑 | ❌ 半实时 | `agent_messages` 其实实时写入，但"外部ID→内部ID"映射在 run 返回后才登记，执行期 `/agents` 解析不到 |

**已实施方案**：
1. **`collecting` 事件携带增量调用明细**：每步 `dispatch` 后与每次步骤内审查后立即
   `drain_call_chains()` 并 `extend` 进总链，把 `call_chain[chain_cursor:]` 以
   `calls` 字段下发（含 `agent / model / capability / status / elapsed_ms`）；
2. **`planning` 事件携带内部 `task_id`**：Worker 在 `on_progress` 中一收到就
   `link_internal_task_id()`，使执行期间 `/agents` 即可关联 `agent_messages`；
3. **前端 `liveChain`**：`AgentInspector` 从 `progressEvents[].calls` 去重聚合成
   与终态 `call_chain` 同构的数组；业务规则为**终态优先、运行中回退实时事件**，
   去重键为 `agent+model+capability+attempted_at`（反思重试会产生新的
   `attempted_at`，因此不会被误合并）。

**测试中发现并修复的缺陷**：初版只在下发前 drain 一次，导致
**步骤内审查（Reviewer）的模型调用未实时下发**——前端实时链路会缺掉"审查"这一跳，
看起来像凭空多出耗时。已改为审查后同样 drain，并加断言锁死。

**验收标准**：
- [x] 执行期间 `/progress` 的 `collecting` 事件携带 `calls` 明细；
- [x] 实测（生图+描述任务）：第 12 秒任务仍在 `processing` 时，
      `image_agent / Tongyi-MAI/Z-Image-Turbo / 4379ms` 已可读；
- [x] 步骤内审查调用同样实时下发（`reviewer_agent` 出现在事件中）；
- [x] 终态调用链无重复条目（逐步 drain + 收尾兜底 drain 幂等）；
- [x] 前端编译与生产构建通过；
- [x] 新增 5 项测试，全量回归 145 passed。

**与 T-06（SSE）的关系**：本工单完成后，2 秒轮询已可看到"逐条跳出"。
T-06 的定位随之明确为**降低延迟到毫秒级并减少轮询开销**，属增强项而非前提——
在没有增量数据的情况下直接上 SSE，只会更快地推送"空数据"。

### T-16 观测视图合并 `P1` 0.5d ✅ 已完成

**问题**：右栏把同一批事件拆成三块分别渲染——
「调用链路」（按角色分组的模型调用）、「协作拓扑」（步骤节点与依赖）、
「协作对话」（派发/回收消息）。三者是同一件事的三种切面，
导致读一次任务要在右栏滚三遍，信息密度低且重复。

**合并后的信息模型**（单棵层级树）：

```
任务
 └─ 步骤(step)          ← 节点骨架
     ├─ 执行角色(agent)  ← 节点标题
     │   └─ 模型调用      ← 节点内联明细
     └─ 产物 / 依赖       ← 节点徽标与依赖标记
```

「派发/交付」属传输层细节，压缩为节点内两行文字（`派发：…` / 产物徽标）；
原始消息保留为节点内**可展开的「原始消息」**——可视化被质疑时能点开看到
未经加工的 `agent_messages` 记录，作为未造假的追溯证据（决策：保留而非删除）。

**必须补的两个数据缺口**（此前做不到归并）：

1. **`CallChainEntry` 缺 `step`**：调用链只有 agent/model/耗时，没有"属于第几步"。
   而 `reviewer_agent` 会在多个步骤各出现一次，**仅按角色名合并会串**。
   已加 `step` 字段并由 `BaseAgent._record_chain()` 传入 `message.step`，
   贯通 `builder` / `storage` 序列化与 `get_task_history` 归一化白名单；
2. **orchestrator 的拆解调用隐形**：`TaskRouter` 直接用 `LLMClient`、不经 `BaseAgent`，
   其耗时从不进调用链，而它常常是最慢的一步（实测 3.8s，慢时可达 30s+）。
   已让 `TaskRouter` 暴露 `last_model_name / last_status`，由 Orchestrator
   在 PLANNING 后补记一条 `step=0, agent=orchestrator, capability=planning` 的调用。

**界面调整**：
- 新增 `CollabView.tsx`：节点内联模型调用明细，降级时自动显示多行并标「降级」；
  节点可展开原始消息；
- 删除 `CollabTopology.tsx` / `CollabConversation.tsx`（已合并，代码进 git 历史）；
- 「编排管道阶段」四段卡片压缩为**一行细进度条**（保留：它是系统级固定状态机，
  答辩讲"状态机设计"时仍需要，但与任务级动态步骤语义不同，故只占一行）。

**验证**：
- [x] 终态调用链按步骤归并正确：
      `step=0 orchestrator/planning` → `step=1 image_agent` →
      `step=2 writer_agent + reviewer_agent`（步骤内审查）→ `step=3 reviewer_agent`（整体审计）；
- [x] 前端节点归并实测：4 个节点（planning / produce / produce / audit），
      产物与依赖标注正确；
- [x] 新增 3 项后端测试；全量回归 **148 passed**；前端编译与构建通过。

**测试中暴露的既有隐患**：`_record_chain` 依赖各 Agent 手写
`model_invoked = True`，漏写则调用链**静默不记录**——正是 T-08 技术债 A 的实例，
测试替身一开始就踩到了。该技术债优先级应提升。
