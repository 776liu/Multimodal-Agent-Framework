# 会话管理方案

## 一、背景与现状诊断

### 1.1 为什么会话管理此前被"砍掉"

项目早期前端为 Streamlit（见 [docs/技术](docs/技术) 问题 1）：Streamlit 的脚本重执行模型 + 单一 `st.session_state` 无法实现真正的多会话隔离，一旦做多会话切换就会出现数据串窗口、渲染残留。因此当时降级为**单会话模式**，会话元数据管理（`sessions` 表 + `save_session`）写好后被搁置，未接入调用链。

现在前端已升级为 React SPA（[docs/前端优化方案](docs/前端优化方案.md)），`sessionStore` 天然支持多会话独立状态，后端 API 层 `session_id` 参数也一直全链路可用——**恢复会话管理的两个阻塞条件都已消除，可以提上来了。**

### 1.2 当前断点诊断（补链前的真实状态）

| 环节 | 现状 | 问题 |
| :--- | :--- | :--- |
| `sessions` 表 | 表结构完好，**0 行数据** | `save_session()` 已实现但全局无调用方，是一张"死表" |
| 会话列表 `list_sessions()` | 能正常返回 | 全靠兜底分支：从 `messages`/`task_logs` 反向推导，标签 = 第一条用户消息截 30 字 |
| 前端"新建会话" | 仅本地 `setState` 造 ID | 后端无感知；刷新后若未发过消息，会话"消失" |
| 会话标签 | 无法自定义 | 永远是首条消息前 30 字 |
| 删除会话 | 只有 `DELETE /history`（清消息+任务日志） | 会话本身无删除入口，`delete_session_data()` 闲置 |

### 1.3 分层职责（保持不变，明确边界）

```text
┌─────────────────────────────────────────────────────────┐
│  SQLite (Storage) —— 持久层（会话管理的唯一真相源）        │
│    sessions    会话元数据（本次补链的核心表）              │
│    messages    对话消息                                    │
│    task_logs   任务日志                                    │
│    task_audits 审计记录                                    │
├─────────────────────────────────────────────────────────┤
│  Redis (RedisTaskManager) —— 瞬时层（不参与会话管理）      │
│    任务队列 + 任务运行状态, TTL 1h                         │
├─────────────────────────────────────────────────────────┤
│  Memory —— 进程内热缓存（会话上下文加速层）                │
│    dict 缓存 + 穿透写 SQLite, 多Agent阶段再扩展agent维度   │
└─────────────────────────────────────────────────────────┘
```

存储选型结论：**SQLite 足够**（实测写入 7800+ 条/秒，读 200 次 0.01s），多 Agent 阶段仅新增 `agent_messages` 表，同量级写入；仅当出现多进程 Worker 部署或远程库访问需求时才迁移 PostgreSQL。

## 二、方案设计

### 2.1 会话生命周期（补链后）

```text
[前端点击"新建会话"]
      │ POST /api/sessions  {label: "新对话"}
      ▼
[sessions 表登记] ──→ save_session(id, label)   ← 补链点 ①
      │ 返回 session_id
      ▼
[用户发送第一条消息]
      │ POST /api/task/submit (带 session_id)
      ▼
[submit 兜底登记] ──→ 若该 id 不在 sessions 表 → save_session  ← 补链点 ②
      │
      ▼
[Worker 完成任务] ──→ 首条消息时自动回填标签 = 首条用户消息  ← 补链点 ③
      │               (label='新对话' 时才回填, 不覆盖用户自定义名)
      ▼
[用户重命名] ──→ PATCH /api/session/{id}  {label}          ← 新增接口
      ▼
[用户删除会话] ──→ DELETE /api/session/{id}                ← 新增接口
      │       级联清理: sessions + messages + task_logs + task_audits + Redis 在途任务
      ▼
[列表刷新] ──→ GET /api/sessions (主分支生效, 兜底分支保留兼容旧数据)
```

### 2.2 接口变更清单

| 接口 | 类型 | 状态 | 说明 |
| :--- | :--- | :--- | :--- |
| `GET /api/sessions` | GET | 不变 | `list_sessions()` 主分支开始生效，兜底分支保留兼容历史数据 |
| `POST /api/sessions` | POST | **新增** | 显式创建会话，body 可带 `label`，返回完整 `SessionInfo` |
| `GET /api/session/{id}/history` | GET | 不变 | 读 messages + task_logs（已有） |
| `PATCH /api/session/{id}` | PATCH | **新增** | 重命名会话标签 |
| `DELETE /api/session/{id}` | DELETE | **新增** | 删除整个会话（级联全部相关数据） |
| `DELETE /api/session/{id}/history` | DELETE | 不变 | 仅清空消息与任务日志，保留会话壳（已有） |

### 2.3 关键设计决策

1. **标签回填不覆盖原则**：Worker 首条消息回填标签时，仅当 `label` 仍为默认值 `'新对话'` 才写入；用户已手动命名则会话标签保持用户主权。
2. **submit 兜底登记**：即使前端跳过显式创建（如旧客户端、脚本直调 API），任何一次 `task/submit` 都保证会话被登记——`sessions` 表从此不会再出现"幽灵会话"。
3. **删除语义分级**：`/history` 是"清空聊天记录"（保留会话），`/session/{id}` 是"销毁会话"（级联删除）。前端侧边栏的删除按钮应对应后者。
4. **兼容性**：历史数据（sessions 表为空的旧会话）继续由 `list_sessions()` 兜底分支识别，无需数据迁移脚本。
5. **存储扩展预留**：`sessions` 表加 `updated_at` 列（`_check_columns` 机制自动补齐，老库无感升级），为多 Agent 阶段按活跃度排序做准备。

### 2.4 前端配合改动（frontend/src）

| 位置 | 改动 |
| :--- | :--- |
| `api/session.ts` | 新增 `createSession(label?)`、`renameSession(id, label)`、`deleteSession(id)` 三个方法 |
| `stores/sessionStore.ts` | `createNewSession` 从"本地造 ID"改为"先调后端再入列"；新增 `renameSession` action |
| `components/sidebar/Sidebar.tsx` | 会话项支持双击/菜单重命名；删除按钮改为删除整个会话并联动刷新列表 |

### 2.5 多 Agent 阶段的衔接（本次不做，只留口）

- `agent_messages` 表（见 [docs/升级计划.md](docs/升级计划.md) 4.5）以 `session_id` 为外键关联，会话删除时级联清理；
- Memory 扩展 `agent_id` 维度后，`delete_session_data` 同步清理各 Agent 的记忆缓存；
- 会话元数据表预留 `updated_at`，多 Agent 看板按"最近活跃"排序直接可用。

## 三、实施与验收

### 3.1 实施顺序

1. 后端 Storage 层：`rename_session()`、`delete_session_data()` 扩展级联、`_check_columns` 补 `updated_at`；
2. 后端 API 层：`POST /api/sessions`、`PATCH/DELETE /api/session/{id}`、submit 兜底登记、Worker 标签回填；
3. 前端：sessionApi 三个新方法 + store 改造 + Sidebar 交互；
4. 端到端验证。

### 3.2 验收标准

- [ ] 前端新建会话后，`sessions` 表立即出现该行（不再是本地假会话），刷新页面不丢失；
- [ ] 发送首条消息后，侧边栏标签自动变为消息摘要（'新对话' 才回填）；
- [ ] PATCH 重命名后列表即时更新，且后续首条消息回填不覆盖自定义名；
- [ ] DELETE 会话后：sessions/messages/task_logs/task_audits 四表无残留，Redis 在途任务被标 FAILED，前端列表移除；
- [ ] 旧数据兼容：历史会话（无 sessions 行）在列表中仍可见、可正常打开。
